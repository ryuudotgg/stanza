## Findings

`--fix` and `--check` print one finding per line:

```text
path:line:col: rule: message
```

A finding that `--fix` leaves for you to fix by hand ends with ` (by hand)`. The line and column count from 1, and the column counts UTF-16 code units, as VS Code does, so a `path:line:col` clicked in a terminal lands on the character.

The path is relative to the working directory, or absolute when stanza cannot read the working directory. A path holding a control character, a line or paragraph separator, `"` or `\` prints quoted, in the escapes `git status` uses, such as `"a\nb.ts"`, so a row always fits on one line, and a row that starts with `"` always holds a quoted path. Findings are sorted by path in byte order, the order `git ls-files` lists them in, then by line, column and rule id. `--check` prints every finding. `--fix` applies what it can and prints what is left, so its findings are the ones no rule could fix.

Given this file at `src/load.ts`:

<include lang="ts" meta='title="src/load.ts" lineNumbers'>
  ../../../../tests/fixtures/after-multiline/example.before.ts
</include>

`stanza --check src/load.ts` prints:

```text title="Finding"
src/load.ts:5:3: after-multiline: add a blank line after the multi-line statement above
```

Besides the rule ids, a finding can name a file stanza cannot handle:

| rule id | meaning                                                                                |
| ------- | -------------------------------------------------------------------------------------- |
| `parse` | the file cannot be read or parsed, and is left untouched                               |
| `error` | stanza failed on the file, or its fixed text would not parse, and it is left untouched |
| `write` | `--fix` cannot write its fixes to the file, or the file changed while stanza ran       |

Each of these makes the run exit 2.

A file nested so deeply that parsing it could overflow stanza's stack is reported with the `parse` rule before stanza parses it, at the point where it passes the cap. The cap is 10,000 levels, or fewer when stanza runs on a smaller stack. Each bracket, brace, template substitution and JSX element is a level. So is each statement head (`if`, `while`, `for`, `with`, `switch` or `do`) whose body is still open, and each token in the same expression that opens a nested one: `=` and the other assignments, `=>`, `?`, `:`, `<`, `**`, `...`, `new`, `await`, `yield`, `extends`, `keyof`, `readonly`, `unique` and `infer`. Other operators, such as `!`, `+`, `|`, `&&` or `.`, count one level for every 16 of them. A comma or a finished statement drops the count of the expression it ends:

```text title="Nested Too Deep"
src/load.ts:1:10010: parse: nests more than 10000 levels deep, left untouched
```

A file that changes after stanza reads it, such as one an editor saves while `--fix` runs, keeps the new text. Stanza reports it and leaves it for the next run:

```text title="Changed File"
src/load.ts:1:1: write: changed while stanza ran, left untouched
```

`--fix` writes a file in place when it cannot replace it, such as a hard link, a file in a read-only directory or a file mounted on its own. If that write fails and putting the original text back fails too, the finding says so:

```text title="Possibly Truncated File"
src/load.ts:1:1: write: cannot write: no space left on device, restore failed, the file may be truncated
```

When stanza hits an internal error on a file, a bug in stanza rather than in the file, it leaves the file untouched, reports it with the `error` rule and goes on with the rest of the run:

```text title="Internal Error"
src/load.ts:1:1: error: internal error (index out of bounds), left untouched
```

It also prints one line on stderr naming the file, the line to quote in a bug report, unless the run uses `--fix --json --stdin`, whose stderr holds only the findings:

```text title="Internal Error on Stderr"
stanza: internal error on src/load.ts, left untouched: index out of bounds
```

An internal error outside any file ends the run with one line on stderr and exit 2:

```text title="Internal Error Outside a File"
stanza: internal error: index out of bounds
```

## Summary

A run of `--check` or `--fix` over paths, `--changed` or `--staged` ends with one line on stderr that counts what it found and did. For the example above, `stanza --check src/load.ts` ends with:

```text title="Summary"
1 finding in 1 file, fixable with --fix
```

| run                               | summary                                                  |
| --------------------------------- | -------------------------------------------------------- |
| `--check` with findings           | `4 findings in 2 files: 2 fixable with --fix, 2 by hand` |
| `--check` with none               | `checked 12 files, no findings`                          |
| `--fix` that rewrote files        | `rewrote 2 files, 2 findings left to fix by hand`        |
| `--fix` with nothing to change    | `checked 12 files, nothing to fix`                       |
| `--changed` with no changed files | `no changed files to check`                              |
| `--check --staged` with findings  | `4 findings in 2 staged files: 2 fixable, 2 by hand`     |

The findings it counts are rule findings. A file that cannot be read, parsed or written, or that stanza failed on, counts among the files checked and in a last clause such as `, 1 file failed`. A file skipped for its generated header does not count. The summary never changes the exit code, and under `--staged` only the [repair lines](/reference/file-selection#staged) follow it.

`--json`, `--stdin`, `stanza explain` and the hook print no summary. Neither does a run that formats no file because every file it picked is generated or every path it was given failed.

## In a Terminal

When stdout is a terminal, `--check` and `--fix` over paths, `--changed` or `--staged` print the fields the fences on this page show in aligned columns. `--json` and `--stdin` keep their own forms. Each file's findings form one group: the location pads to the widest location in the group and the rule to the longest rule id, two spaces follow each, and `(by hand)` follows the message after two more. A blank line separates the groups and comes before the summary.

A terminal also gets color, each stream on its own: stdout when stdout is a terminal, stderr when stderr is. On stdout the location prints bold, the rule dim and `(by hand)` yellow. On stderr the `stanza:` or `stanza hook:` prefix prints bold red on an error, a failure that makes the run exit 2, or 1 for the hook, and bold yellow on a notice, and the numbers in the summary print bold. Color never says anything the plain text does not. Under a coding agent, stanza prints the one finding per line form above even on a terminal. [Environment](/reference/cli#environment) lists the variables that turn color off or force it on.

## Working Directory

Stanza needs the working directory only to read relative paths, `--changed`, `--staged` and `stanza explain`. When the directory it was started in has been deleted, `--check` or `--fix` over absolute paths goes ahead as usual and prints them as absolute paths. Any other run prints this and exits 2:

```text title="Deleted Working Directory"
stanza: cannot read the working directory: no such file or directory
```

## JSON

`--json` prints the findings as one JSON array instead. `fixable` says whether `--fix` applies the finding. For the example above:

```json title="--json"
[
  {
    "path": "src/load.ts",
    "line": 5,
    "col": 3,
    "rule": "after-multiline",
    "message": "add a blank line after the multi-line statement above",
    "fixable": true
  }
]
```

## Stdin

With `--stdin <path>`, stanza reads the source from stdin. The path only names the buffer: it picks the extension, the lint config and the skip rules, and need not exist.

| mode              | stdout         | stderr        |
| ----------------- | -------------- | ------------- |
| `--fix --stdin`   | the fixed text | findings      |
| `--check --stdin` | findings       | warnings only |

A path the skip rules exclude passes through untouched: `--fix` prints the input as it came. For format on save in an editor, see [Editors](/guides/editors).

When `--fix --stdin` reads the input but cannot format it, because the path is not TypeScript or JavaScript, its folder cannot be read, git fails, or the working directory is gone, it prints the input unchanged on stdout, one `stanza:` line on stderr, and exits 2. With `--json`, the failure is an `error` entry in the findings array instead of that line, so stderr stays one JSON array. The entry's path is the path as given:

```json title="Stdin Failure"
[
  {
    "path": "notes.md",
    "line": 1,
    "col": 1,
    "rule": "error",
    "message": "not a TypeScript or JavaScript file: notes.md",
    "fixable": false
  }
]
```

When stdin itself cannot be read, stdout stays empty and the entry's message starts `cannot read stdin:`.

## Warnings on Stderr

Warnings and notices go to stderr and never change the exit code. The notice stanza prints when it cannot tell whether a lint config enforces braces is covered under [Braces and Lint Config](/rules/braces-and-lint-config).

When stanza cannot read the line width from a config file it finds, it prints this warning unless the run uses `--fix --json --stdin`. The warning names each file it cannot read: an oxfmt, Biome or Prettier config, a `package.json`, or an `.editorconfig`. Here it is for an unreadable `.oxfmtrc.json`:

```text title="Width Warning"
stanza: cannot read the line width from .oxfmtrc.json, so the next source sets it
```

Stanza takes the line width from the next source it checks.

When the system will not start a worker thread, under an address space limit for example, stanza formats that thread's share on the threads it has and prints one warning for the run:

```text title="Worker Warning"
stanza: 2 of 3 worker threads failed to start, so the run went on without them: resource temporarily unavailable
```

`stanza hook` prints the same warning as a notice with the `stanza hook:` prefix, and the warning does not change its exit status.

## Unwritable Output

When stanza cannot write its findings or its fixed text, on stdout or on the stderr that `--fix --stdin` prints findings to, it prints this on stderr and exits 2, since whatever reads the output never got the results:

```text title="Unwritable Output"
stanza: cannot write output: no space left on device
```

A warning or notice that cannot be written changes no exit code. A reader that stops early, as `| head` does, is not a failure either, and the run keeps its own exit code.

## Exit Codes

| exit | `--fix` and `--check`                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | clean, or nothing was selected                                                                                                                                                                                                                                                                                                                                                                                                               |
| 1    | findings remain                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 2    | a usage error that names the problem, a missing or unsupported path, a path that is not a regular file, a file name that is not valid UTF-8, a file that cannot be read or parsed, fixes that cannot be written or a file that changed while stanza ran, an internal error, a git command that failed while picking files, a working directory stanza cannot read when the run needs it, or [output stanza cannot write](#unwritable-output) |

Exit 2 wins over 1. A file that fails is reported and left untouched, and the rest of the run still goes ahead.

Under `--fix`, exit 1 means findings remain that `--fix` cannot apply, so an editor that formats through `--fix --stdin` has to accept 1 as success.

[`stanza explain`](/reference/explain#exit-status) and [`stanza hook`](/reference/hook-protocol#exit-status) have their own exit codes.
